# agent-ui: instructions for working on the framework

This file is for an agent working on the framework repository itself: the runtime, the validator, the bundler, the servers, the docs, the cookbook and the examples. It is **not** the guide for an app. An agent that writes an app reads `docs/AGENT-RULES.md` (shipped in the package) and `docs/GUIDE.md`; the block `agent-ui init` writes into a project points there. This file is not published with the package.

Every path below that starts with `src/`, `docs/`, `build/`, `test/support/` or `examples/` is relative to this package directory. In code that uses the package, import by name: `import { app } from '@ehtb/agent-ui'`, `import { withResources } from '@ehtb/agent-ui/resources'` (the table is in `docs/API.md`, "Importing"), and run the tool as `agent-ui build | dev | serve | check | schema | explain | init`. The `npm` scripts named below exist in the framework repository only.

The framework builds UIs with `agent-ui`: **the UI is a JSON spec that an app author writes with the builders of `@ehtb/agent-ui/spec`, state is plain data in signals grouped in namespaces, and all behavior goes through named, typed actions.** Priorities: performance, accuracy, size. Code is written in readable English names and is never minified by us (that is a separate, later step). Do not import React, Vue or similar, and do not add dependencies (network installs may be blocked).

Before you write or change a page for an example, a fixture or the cookbook, run `agent-ui explain` and copy the recipe in `cookbook/` that is closest to the task (`agent-ui explain <recipe>` prints its files; `agent-ui explain <topic>` prints the one valid form of a part of the grammar). Every recipe is a page that `agent-ui check` renders and the tests drive, so it is known to work.

Read order for work on the framework: this file and `docs/AGENT-RULES.md` (the rules an app author follows) always; then the doc of the area you change, the section, not the whole file: `docs/GUIDE.md` (how pages, URLs, APIs and forms fit together), `docs/API.md` (grammar, semantics, testing helpers), `docs/BUILD.md` (bundling, the servers, budgets), `docs/DESIGN.md` (the record of decisions: why, evidence, what is deliberately not built). `README.md` is the overview and the state model. Runnable example apps live in `examples/` (`examples/README.md`); they use the framework and the framework never depends on them. `examples/shop` is the code splitting example (several apps from one source tree sharing a chunk), with measured sizes, how it works and its limits in its README. Runtime: `src/ui.js` (read it whole before changing it).

## Commands
In a project that uses agent-ui (the `agent-ui` command comes with the package; options in `docs/BUILD.md`):
- `agent-ui build` writes `dist/` (production: hashed, stripped, **validator omitted**); `agent-ui build --dev` is readable with the validator; `agent-ui serve` serves the build, rendering every page on the server for the URL asked for (and answering the project's API); `agent-ui dev` serves with hot reload (the edited page is swapped in place, keeping its state) and rebuilds on change; `agent-ui schema` writes the spec schema to `./spec.schema.json`.
- `agent-ui check` renders every page in development mode and reports spec, link and data problems; run it before finishing.
- `agent-ui init` writes the rules for agents into the project's `AGENTS.md`; `agent-ui explain [recipe or topic]` prints the one valid form for a task (the cookbook, `cookbook/`) or for a part of the grammar. `agent-ui build --source-maps` writes a `.map` file next to every chunk.

In the framework repository (Node 22, zero dependencies):
- `npm test` runs everything headless: `npm run test:framework` (`test/*.test.mjs`: runtime, validator, plugins, server, bundler, package, docs; it uses only `test/fixtures`, never `examples/` or `cookbook/`) and `npm run test:examples` (`test/examples/`: the examples' documentation, the cookbook's recipes and the migration skill; then every example in `examples/` as a standalone project, installed and tested on its own; see `examples/README.md`). `npm run example -- <name> <script>` runs a script of one example. `npm run typecheck` checks the declarations (needs `tsc`, run separately). `npm run schema` regenerates `docs/spec.schema.json`.

## Layout
The package has four code folders, each with one responsibility and a one-way dependency (`test/layers.test.mjs` enforces it): `src/` <- `server/` <- `build/` <- `cli/`.
- `src/` is the runtime and the pure libraries around it; it runs in the browser and on the server and imports no Node built-ins. `src/ui.js` core runtime. `src/validate.js` spec validator and `grammar` (left out of production builds). `src/spec-core.js` primitives shared by both. `src/grammar.js` the tables of the grammar (tags, operand counts, element keys, attributes, window events, name patterns), written once and read by the validator, the builders' checks, the schema and the `grammar` export; `src/handler-checks.js` the shared checks of a handler `[action, args?, options?]` (argument names, options, key chords), used by the validator and `windowEvents`; `src/spec-walk.js` the traversal for finding or listing the nodes below a node (`visitSpec`; the validator, component expansion and page checks walk with their own context). `src/namespaces.js` how namespaces are declared and flattened (names, qualified keys, nesting, `rowState`). `src/runtime-checks.js` the development-only checks of the runtime (left out of production builds, like the other `*-checks.js`); `src/errors.js` and `src/error-messages.js` how the runtime makes an error: a code (AUI + 4 digits), small details and, in development only, the sentence of the catalogue (a production error is the code and the details; `decodeError` reads either form). `src/mount-element.js` `mountElement(api, id, mount)`: how a plugin that draws (a chart, an editor) claims an element by its explicit id; only the plugins that import it pay for it. `src/http-headers.js` the one check and merge of response headers (API, form and `transformResponse` headers; public as `@ehtb/agent-ui/http-headers`). `src/resources.js` async data (a plugin a page lists, so a page only downloads what it imports; there is no storage plugin and no client-side router: durable state lives on the server and a link is a page load). `src/url-pattern.js` the URL patterns pages and API tables share. `src/window-events.js` window/document events (checked at install by `src/window-events-checks.js`, left out of production builds). `src/spec-tools.js` atomic spec patches. `src/components.js` spec components (`expandComponents`; params may declare defaults, variants and optional props). `src/memoize.js` `memoizeItem`, per-item caching for derived lists. `src/sync-apps.js` `syncApps`: one-way sync between two separate apps on one page, nothing else (never use it inside one app). `src/shell.js` `defineShell`: the part of a document that stays while the page changes, an app of its own that reads the page one way; `src/navigation.js` `withNavigation`: soft links (`a({ href, soft: true })`) and `route.go`, a page load made faster, with the page destroyed (`app().destroy()`) and replaced inside the shell. `src/head.js` what a page says about its document (title, description, the attributes of `<html>` and `<body>`, the elements of `<head>` and the end of `<body>`): resolved for a state, applied to a browser document; the server's half is `src/head-document.js` (the full description, with the text of scripts and styles, and the names the checks share; production browser bundles leave it out) and `injectHead` in `server/document.mjs`. `src/hot.js` the hot swap of the running page for `agent-ui dev` (a stub in production builds, `build/stubs/hot-omitted.js`). `src/pages.js` pages (`definePage`, `startPage`; its development checks are `src/pages-checks.js`, its server-only half `src/pages-server.js`: status and the document; production browser bundles swap them for stubs in `build/stubs/`). `src/hydrate.js` the browser side of server rendering and the ids it shares with the server (`APP_ELEMENT_ID`, `STATE_ELEMENT_ID`); `src/adopt.js` the cursor with which the first render takes over the nodes the server wrote (`adopt: true`; a difference is made again at the node and reported as `AUI0305`; the words of a difference are in `src/runtime-checks.js`); `src/nesting.js` the nestings an HTML parser rewrites, which the validator refuses; `src/document-markup.js` writes the markup a page's document carries (state script, entry script, stylesheet links); `src/document-markup-reader.js` reads it for soft navigation and accepts attributes in any order; `src/server-dom.js` the DOM it renders into. `src/devtools.js` lazy debug panel. `src/spec-schema.js` the JSON Schema of the spec. `src/*.d.ts` types.
- `server/` turns a page into an HTML document, in Node: `server/render-page.js` (`renderPage`, and the default `fetchFunction` that explains how to configure one), `server/document.mjs` (markup, title and description into the page template) and `server/request.mjs` (the shared request context: method, pathname, search, query, headers and cookies; `isLocalPath`; `requestContextForUrl` for a form outcome page; the URL of a request target; and the Host check against DNS rebinding), `server/file-types.mjs` (content types, the headers every answer carries, what is a file), `server/ssr-handler.mjs` (`createSsrHandler`, a request handler for the host's own server: renders the pages with real URLs and handles the `api` module; its `initialStateFor` and `transformResponse` hooks add public state and change an answer's headers or body; it serves no files, because the framework ships no production server).
- `build/` turns source into a site: the bundler (`build.mjs`, module graph, `assign-chunks.mjs` (chunks by the set of pages and the owner: framework, npm package or app), `generate-chunks.mjs` (with `source-map.mjs`: the build's line maps, composed with a `transform`'s own map), `write-site.mjs`), `presets.mjs` (framework build options), `pages.mjs` (finds the pages in the folders, generates their entries into `.agent-ui/` and writes each page's finished spec there as data, and each shell's content once), `css-graph.mjs` (`@import` graph of `page.css`/`style.css` and the browser-only style modules it generates), `config.mjs` (loading `build.config.mjs`), `prerender.mjs` (static generation), `leak-check.mjs` (the build warning when a browser bundle holds the spec builders), `package-name.mjs` (the package's name, read from `package.json`, for generated code and checks).
- `cli/` is the `agent-ui` command (`build`, `dev`, `serve`, `check`, `schema`, `explain`, `init`), wiring the three folders together. The development server lives here, because a deployed site is served by the host: `cli/static-handler.mjs` (with `cli/safe-path.mjs`), `cli/ssr-server.mjs` (the render handler in front of it: what `agent-ui serve` runs) and `cli/hot-reload.mjs` with `cli/hot-client.js` (hot reload, plugged into the static handler by its hooks) and `cli/hydration-check.mjs` (what `agent-ui check` says about hydration: a browser's first render of each page compared with the server's markup and, under another time, time zone and locale, with itself). No other folder of the framework imports from it.
- `cookbook/` is a project inside the package (not a code folder): one page per common task, listed in `cookbook/recipes.mjs`, which `agent-ui explain` prints and `test/examples/cookbook.test.mjs` runs. It is the package's few-shot memory: when you add a pattern that agents should copy, add it here with a test, not only to the docs.
- Project layout (as in `examples/<name>/`): **a page is a URL, a URL is a folder, and a page is two files.** `pages/page.js` + `pages/view.js` are `/`, `pages/about/page.js` + `pages/about/view.js` are `/about`, `pages/event/[id]/page.js` + `.../view.js` are `/event/:id`; nothing lists the pages and `agent-ui build` generates the browser entries. `page.js` exports `page = { head, namespaces?, plugins?, ready?, status?, shell?, debug? }` — behavior only (`src/pages.js`, `docs/API.md` section 13, `docs/GUIDE.md`); `view.js` exports `view` (the content, required) and optionally `layout` and `pending`. Only the server and the build import `view.js`: a production build evaluates it once in Node and ships the finished spec as data, so a browser downloads the page's behavior and the spec, never the builders that assemble it. Beside them: `page.css`, `api.js` (its server side; the project's own `api` module composes them, `examples/events/compose-api.js` is one to copy), helpers. `pages/style.css` styles every page. Both CSS entry points may `@import` shared CSS; the build follows that graph and links a file imported by a subset of pages only to those pages (`docs/BUILD.md`, "CSS imports"). Shared namespaces and shared components are modules you import, one component per module (the bundler includes whole modules). `public/` is copied to the site root. Keep `window` and fetch injectable so tests run headless. Add a page: create its folder with a `page.js` and a `view.js`, run `agent-ui check`.
- A project's build config is a `build.config.mjs` function of the mode (`build/presets.mjs` supplies the framework settings; each example's own `build.config.mjs` is a model; `--config` names another file). `test/` is the single test folder: `*.test.mjs` are the framework's tests, `test/fixtures` are stable test apps (independent of `examples/`; a framework test never reads `examples/` or `cookbook/`, `test/isolation.test.mjs` enforces it, and builds or serves a project through `test/copy-fixture.mjs`, which copies a fixture and links the package; tests of the examples and the cookbook are in `test/examples/`), and `test/support` holds `dom-shim.mjs` (mutation-counting DOM), `helpers.mjs` and `json-schema.mjs`, which are published and imported by any project's tests as `@ehtb/agent-ui/testing/dom-shim.mjs` and so on.

## Code style
- Readable English names everywhere, including the grammar (`tag`, `props`, `children`, `classes`, `{state}`, `{item}`, `{event}`, `{equals}`). No abbreviations (`st`, `g`, `el`), no one-letter variables except trivial loop indexes. Normal formatting, short comments that explain why.
- One definition per helper: `isPlainObject`, `toArray`, `isSameValue`, `readEventPath`, `eventKeyName` live in `src/spec-core.js` (`src/ui.js` re-exports them); the DOM implementation lives in `src/server-dom.js` (the test shim extends it). Reuse them, do not copy them. Browser entries call `startPage(page, { ..., dev })`, where the build writes `dev` down (it is `create(browserEnvironment({ dev }))` underneath).
- Imports in the dialect the bundler supports (`docs/BUILD.md`): relative paths with extension, named or namespace imports, no default exports or imports in your own files (files of a package, linked or not, may have them), no cycles, no `export let`. A package written with `export *` or re-exports (zod, Tiptap) cannot be bundled as it is: keep importing it by name and give the browser bundle a one-file esbuild build of it through `replaceModules` (`docs/BUILD.md`, "Vendor files"; `examples/with-typescript/vendor/zod-entry.js` is the model).

## Hard rules
- **No external dependencies (requirement).** Do not add anything to `dependencies` or `devDependencies`, do not import npm packages in `src/`, `build/`, `test/support` or tests, and do not vendor third-party code. Use Node built-ins and native browser APIs only. If a task seems to need a library, write the small piece yourself or expose a hook (like `transform`) so the user can plug a tool in from outside. The requirement is about the framework (the repository's `package.json`, `src/`, `server/`, `build/`, `cli/`, `bin/`, `test/`). Five examples, `with-express`, `with-fastify`, `with-tailwind`, `with-typescript` (TypeScript checks its JavaScript with `checkJs`, and zod checks the responses of its resources) and `react-converted-components`, are separate projects whose purpose is to show agent-ui next to those libraries (the last one, Chart.js drawn by a `mountElement` plugin on its `/charts` page): they declare them in their own `package.json`, nothing in the framework imports them, and you may work on them (installing needs the npm registry). A sixth, `events`, declares one build tool, `esbuild`, as a `devDependency`: its `build.config.mjs` passes it to the `transform` option to minify production builds (`docs/BUILD.md`). It is a build step of that project, the framework does not import it, and the example builds in development mode without it being used. Because `events`, `with-typescript` and `react-converted-components` have dependencies of their own, `npm test` skips them and `node test/run-examples.mjs --all` (or `npm run example -- events test`) runs them.
1. **State is immutable, JSON-serializable data, in namespaces.** Every state key, derived value and action belongs to one namespace (`todos.draft`, `todos.add`). Replace, never mutate. Dev mode freezes state and turns violations into logged errors. See "State management" below.
2. **Only actions write state, and an action writes only its own namespace.** Spec handlers are `[actionName, {args}]` (or a list of them) with no logic. A change in another namespace goes through `calls`. Actions never touch the DOM, timers or network.
3. **Declare every action argument** in `args` (`'string'`, `'number'`, `'boolean'`, `'json'`) and pass exactly those in handlers. Make actions idempotent where an event can repeat (blur after Enter).
4. **Derive, don't compute in the spec** for anything over whole lists; use spec operators (`length`, `equals`, `greaterThan`, `and`, `or`, `join`) for row-level or one-off conditions and text.
5. **Every list has a unique, stable `key`** (`"."` for lists of strings/numbers), unique across the whole list, also in lists built in `derive` or `initialState`: a duplicate drops the later item. Replace changed items; unchanged items keep their reference.
6. **Give an explicit, unique `id`** to anything tests or other agents address. Default ids are spec paths and shift when siblings change.
7. **External effects live in plugins** and talk to the app only through `api.watch` and `api.dispatch`. Network goes through `resources` (logged actions of the namespace that declares them), never `fetch` inside an action. Plugins must stay quiet while `api.replaying`.
8. **Accessibility and safety are validated:** inputs/selects/textareas need `aria-label`, images need `alt`, buttons/links need text or a label, no `javascript:` URLs.
9. Durable data and state live on the server (loaded with `resources`); the framework has no browser storage. No `Date.now()`/`Math.random()` in actions (replay must be deterministic); ids and counters live in state.
10. **No new node kinds, events, operators or plugins without** updating the validator, `docs/API.md` and a test in the same change. The grammar stays closed.
11. Never hand-edit `dist/`. Change the source and rebuild.
12. **Accuracy: guide, never leave room for interpretation.** Anything an agent writes has one valid form that the code states. When you add or change an API: (a) fix its shape (required keys, allowed keys, allowed values) and reject everything else, never ignore unknown input; (b) give unknown keys a "Did you mean" suggestion; (c) write every error as `where: what is wrong. How to fix it` and name both sides of a clash; (d) check at the earliest moment (composition, build or mount, not first use); (e) add a test that asserts the message text; (f) keep every comment and doc true to the code as it is now: `test/docs.test.mjs` fails when a mentioned file, `npm run` script, `agent-ui` command or import specifier does not exist, so update docs in the same change. Prefer an explicit list or table over inference from file names or conventions. Messages come from one place: `fail(where, problem, fix)` and `didYouMean(word, candidates)` in `src/messages.js`, and HTML escaping from `src/html-escape.js`; do not write a second copy of either. An error the runtime reports or throws while the app runs (not a check that only exists to be fixed while writing) has a code (`AUI` + 4 digits), small plain details and an entry in `src/error-messages.js`, made with `codedError(code, details, context)` (`src/errors.js`); add the row to the error-code table in `docs/API.md` section 9 in the same change (`test/error-codes.test.mjs` fails when a code is missing from either). The build configuration (`build/config-check.mjs`) and the command line options (`cli/arguments.mjs`) are checked the same way; a new option goes into those lists in the same change.
13. **Code that only runs in development must also work when `dev` is false.** The `*-checks.js` modules and `src/validate.js` are replaced by stubs in production builds, but the real module can be in a production build (`--validator=include`, the validator chunk) and an app can be made with `dev: false` while it is. So a function in such a module must accept what `src/ui.js` passes when it is not in development (a `null` record, a missing option), the stub in `build/stubs/` must export exactly the same names, and a new check gets a scenario in `test/runtime-checks.test.mjs`, which runs the app with `dev: true` and `dev: false`. A test that only runs in development, or only against the stub, does not show that the check is safe.
14. **Prefer a hook or a plugin over framework code.** Before adding a key, option, node kind or behavior to the core, ask whether the app can supply it through an existing extension point (`plugins`, `resources`, `initialStateFor`, `transformResponse`, `createApi`, `build.config.mjs`, `transform`/`replaceModules`, or the host server) or through one small new hook. Add to the core only what the framework must own to write a correct, validated response or what every app needs (state, actions, the request context, status, form outcomes, security checks). Keep optional features — a session store, an auth flow, a CSP policy, a cache layer, a deployment adapter, a component set — in the project or a plugin; do not grow the framework into them. A new core feature still follows rule 10 (closed grammar) and rule 12 (shape, messages, docs, types, tests).

## State management (read before touching state)
Flow is one way: state, then `derive`, then spec bindings, then one DOM property. Events go back only as `[actionName, args]` handlers calling an action, and only an action's `run` calls `store.set`, on its own namespace. State is declared as `namespaces: { todos: { state, derive, actions }, search: { ... } }`; under the hood each `namespace.key` is a signal and a write replaces the whole key. Full description and limits: `README.md` ("State management") and `docs/API.md` section 4.

Do:
- Put every piece of state, including UI-only state (`editing.id`, `draft.title`, `search.query`, open panels), in a namespace of `namespaces`, addressed by id, and change it only through an action. One namespace per concern; a namespace is what you edit, and what a route folder or a reusable feature maps to.
- Write names in one form. Outside a namespace everything is qualified: `{state: 'todos.draft'}`, `'todos.add'`, `ui.state().todos.draft`. Inside the code of a namespace (its actions and derived values) its own keys are plain (`store.get('draft')`, `get('items')`) and other namespaces' keys, for reading only, are qualified (`get('search.query')`). Names are identifiers: letters and digits, starting with a lowercase letter, no dots or dashes.
- Keep state JSON-serializable: strings, numbers, booleans, null, arrays, plain objects. No functions, `Date`, `Map`, `Set` or class instances (replay and server-to-browser state transfer depend on this).
- Replace values, never mutate: `store.set('items', [...items, item])`. Unchanged items must keep their reference (row reuse and `derive` equality depend on it).
- Name a namespace for the concern it holds (`todos`, `search`, `editing`) and an action for what it does (`add`, `setDraft`, `toggle`); the action is then `todos.add`.
- Before writing across namespaces, check whether the state is in the wrong namespace or should be derived. If an action really has to change another namespace (add the todo, then clear the search), list the other namespace's action in `calls` and run it with `call('search.clear', {})`: the owner does the writing, one level only (a called action cannot call further), all of it is one log entry, and everything is undone if any part throws. Or, when it is wiring in the view and not a consequence, give the event a list of handlers: `on: { click: [act('todos.add', {}), act('search.clear')] }`.
- Write specs with the builders from `@ehtb/agent-ui/spec` (`div(null, 'text')`, `button({ on: { click: act('todos.add', {}) } }, 'Add')`, `state('todos.draft')`, `each`, `when`), not by hand-writing JSON: they return the same JSON (the wire format), and a wrong call fails at its line with the fix. `id` is the spec address, `domId` the HTML id. Components: `defineElement(name, { params, spec })` with `param`, `paramKey`, `slot`.
- Share state logic by defining a namespace once and mounting it under several names (`namespaces: { sidebar: disclosure, help: disclosure }`), or a function that returns one from options (`textField({ validate })`).
- Pass state that arrives from outside (server-rendered) as `initialState: { namespace: { key: value } }`; `ui.state()` and `ui.derived()` have the same shape.
- State that every row of a list has (open, selected, a draft) is `rowState: { open: false }` in the namespace, written with `store.setRow(id, { open: true })` (`getRow`, `clearRow`), read in the row with `rowState('namespace.open')`. It is stored as the one state key `namespace.rowState`, only rows that differ from the defaults. A row's state stays when its item leaves the list until the owner forgets it: call `clearRow` from the removing action through `calls`. Do not build a keyed map by hand.
- A nested `each` that needs an outer row says `as` on the outer one, `each(source, key, template, { as: 'order' })`, and reads it with `row('order.id')` (in bindings and handler arguments, at any depth); `item(...)` stays the innermost row. Do not copy outer fields into inner items in `derive`.
- Format numbers, dates and money in `derive` with `Intl`, one display row per item, with `memoizeItem` so a change formats one item (recipe `format-values`). The grammar has no formatting operators and none will be added.
- Dragging a row is pointer events calling actions, not an HTML5 drag-and-drop API (the grammar has no `dragstart`, `drop` or `dataTransfer`): copy recipe `drag-reorder` (`follow`, `transition`, the keyboard path, Escape) and do not look for another way (`docs/API.md`, "Drag and drop").
- A plugin that draws into an element (a chart, an editor) calls `mountElement(api, 'element-id', (element, { key }) => cleanup)` from `@ehtb/agent-ui/mount-element`; the element has an explicit id and no children in the spec, the plugin writes into it, and what happens in it goes back as `api.dispatch(...)` (recipe `draw-into-element`).
- Declare the item shape of lists in `shapes: { items: { fields: { id: 'number', title: 'string' } } }` (optional, `validate` hooks in a runtime type checker such as zod): `{item}` typos fail at mount, and writes are checked in development.
- Compute anything over a whole list in `derive`. A nested `each` reads an outer row with `as` and `row(...)` (above), never by copying outer fields into the inner items.
- A thrown error is reported and every write of that action (and of the actions it called) is undone; nothing partial is left behind.
- Treat `derive` functions as pure and synchronous; they may read other namespaces' keys, qualified.
- A resource belongs to the namespace that declares it (`resources: [...]` next to `actions`) and drives that namespace's actions by verb; its output is written only by its lifecycle actions (`owns`); to restart it, change a watched key (a retry flips a watched flag, as `lookup.ordersCancelled` does in `examples/orders`), and use `onIdle` to clear owned state when `request` returns `null`.

Do not:
- Write state from a binding, a plugin callback or an event handler, or read state from the DOM. Write another namespace's state from an action: use `calls`.
- Do async work, timers or `fetch` inside an action (declare a `resources` entry instead), or use `Date.now()` / `Math.random()` (ids and counters live in state).
- Create hidden state in closures, module variables or DOM attributes, or invent local component state, nested namespaces or two-way binding sugar. The model has these known limits: namespaces are one level, no component-local state (per-row state is `rowState`), derived lists recomputed in full (O(n)), no undo/redo, no virtualization. If a task needs one of them, say so and propose the change instead of working around it with a hack; adding it means updating the runtime, validator, `docs/API.md` and a test together (rule 10).

## Loop for every change
1. Edit the namespace (state/derive/actions) and the spec. 2. `validate()` runs on mount: fix every `specPath: problem` line (typos, wrong argument names, missing labels are all reported). 3. Add or extend a test (run it with `dev: false` too when the change touches a development-only check, rule 13) that dispatches actions and asserts `ui.state()`, `ui.derived()`, `ui.outline()`, `ui.tree()` and `ui.errors` (`await ui.settle()` first; `flushAsync(ui)` when fetches are involved; `assertRepeatable(ui, action, args)` on idempotent user actions such as form lookup, selection and retry; `assertNoErrors(ui)` after the step that opens a branch, since a list in a branch the first render did not show is checked at mount, but only on the data it has then). Then run `agent-ui check`: it reports a duplicate or missing list key anywhere in the spec. 4. `npm test`. A change to the first render or the markup the server writes (`src/ui.js` compile functions, `src/server-dom.js`, `src/adopt.js`) is also run in Chrome: `npm run example -- shop test` and `node --test test/adopt-browser.test.mjs`, because the shim does not parse markup as a browser does. 5. Reproduce a bug as an action log and keep it as a regression test (`ui.replay(log)`). 6. If you changed the grammar, run `agent-ui schema` and update `src/ui.d.ts`. 7. If you touched bundling, read the chunk report from `agent-ui build`; for a build you need to debug, `agent-ui build --source-maps`.
8. When the change is a pattern others should copy, add or update the recipe in `cookbook/` (and its test in `test/examples/cookbook.test.mjs`).

## Orient yourself in a running app (no screenshots)
`window.__ui` in the browser, or the object returned by `create()`: `state()` and `derived()` (nested `{ namespace: { key } }`), `actions()` (qualified names and argument types), `keys()`, `get(key)`, `tree()` (interactive elements, values, bound actions), `outline()` (the rendered structure with text, classes and values), `log`, `errors`, `replaying`. Drive it with `dispatch(name, args)` (returns `undefined` or an error string). The allowed grammar is queryable: `import { grammar } from './src/ui.js'`. Making an app with `debug: true` (`app({ ..., debug: true })`, `debug: true` in a page's `page.js`, or in `defineShell`) makes the browser console show the app: the state as a table, then a collapsed group per action with its arguments and the state and derived values it changed (`src/devtools.js`); `onAction(handler)` is the hook it uses. For what a real browser does that the test DOM does not, `@ehtb/agent-ui/testing/browser.mjs` drives headless Chrome over the DevTools protocol (no dependency; `examples/todomvc/browser.test.mjs` runs one session in both and compares the results step by step).

## Don't
Read the DOM to get state. Use `innerHTML`. Put logic in handlers. Use `div` plus click instead of `button`. Rely on microtask timing: always `await ui.settle()`. Claim browser behavior from shim tests alone: the shim is not a browser. Add component instances with their own state, scoped CSS, a template DSL or two-way binding sugar: out of scope, see `docs/DESIGN.md`. Reuse spec fragments with `expandComponents` and state logic with a namespace mounted under several names; convert a React component by following `docs/CONVERTING.md`; migrate a whole existing app, whatever it was built with, by following the skill `skills/migrate-to-agent-ui/SKILL.md` (in a project: `node_modules/@ehtb/agent-ui/skills/migrate-to-agent-ui/SKILL.md`; copy the folder to `.claude/skills/` to load it as a skill); animate with `transition` plus CSS; render on the server with `renderPage`; make a folder with a `page.js` when a new URL is needed (there is no client-side router; `soft: true` links inside a shell make a page load faster, `docs/GUIDE.md`).

## The block `agent-ui init` writes into a project
The text lives in `docs/AGENT-RULES.md`, between its `project-block` markers: that is the guide an app author reads, and `agent-ui init` copies the block from there into the project's own `AGENTS.md` (with `{package}` replaced by the package name). Keep it to the rules that cost the most when missed. The root file (this one) is for work on the framework and is not published, so do not point a project at it.
