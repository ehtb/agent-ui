# Events (largest example)

Production builds are minified with esbuild, plugged into the `transform` option of `build.config.mjs` (the only dependency of this example, a `devDependency`; development builds stay readable), and carry source maps: esbuild returns its own map and the build follows it back to the source files, so a stack trace in the minified site names `pages/event/[id]/page.js` and its line (`docs/BUILD.md`, "Source maps"). Run `npm install` here first. Event listing and sign-up: a list with search and category filters, static pages (about, faq), an event page with a sign-up form, a JSON API with plain HTML form fallback (`api.js`), a plain static `terms.html`, per-request rendering of every page, and takeover by the browser app. Structure: every folder below `pages/` with a `page.js` is a page, and the folder mirrors its URL (`/event/:id` is `pages/event/[id]/page.js`); the contact page has its own layout, state and API. `pages/event/archived` (`/event/archived`, a literal), `pages/event/[id]` (`/event/:id`, one segment) and `pages/event/[...path]` (`/event/*path`, the wildcard: everything deeper, answered with a 404) show how overlapping patterns resolve: the most specific wins. `ready` and `status` in a page say when its data has loaded and which HTTP status it answers (404 for an unknown event, `event-unknown` always 404); `pages/shared.js` holds the shared `events` namespace, `pages/layout.js` the two shells (`site`, `focused`, view-only), and each page keeps its behavior in `page.js` with its content in the `view.js` next to it; `api.js` composes each page's server side with `compose-api.js`. Moving between pages is a page load: the links are plain, and the pages are prerendered, so the next page arrives finished. `app.test.mjs` is the end-to-end suite: a real build, a real HTTP server, and the browser app on the DOM shim.

Building it found two framework faults that the unit tests had missed, both fixed with regression tests: (1) a `when` or `each` that is a direct child of a `when` branch could not be removed, because the branch only remembered its top-level nodes (a nested control node is an empty fragment once inserted), so switching views left the old one in the DOM; branches now live between two markers and are removed as a range; (2) effects of such nested branches were not disposed with the enclosing branch and kept updating detached nodes. It also needed four additions, each tested: failed responses surface a server `message`, `renderPage` accepts `initialState`,  the server can answer API calls and plain form posts. Remaining honest limits: the server keeps its registrations in memory; hydration still replaces markup; the events app is tested on the DOM shim, not in a real browser.
