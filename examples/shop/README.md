# Shop: code splitting by page, and a shell that stays

**This is the example that shows code splitting working.** A list, a product page and a checkout are three pages of one site, and each page is its own entry: `pages/page.js` (behavior) with `pages/view.js` (content) is `/`, and likewise `pages/product/[id]/` and `pages/checkout/` each hold a `page.js` and a `view.js`. A visitor downloads the code of the page they open and the code the pages share, nothing else: the checkout page never carries the list's product card, and the list never carries the checkout form. What the pages share as behavior is written once in `shared/` and the build puts it in a chunk that all of them load and the browser caches. The `view.js` files and everything only they import (the shell's content, the components, the spec builders) are used when the site is built to render each page's finished spec as data, and never reach a browser. There is no configuration for any of it: the folders are the pages.

**It is also the example for soft navigation.** The three pages live in one **shell** (the header with the cart badge, and the footer), which stays while a link marked `soft: true` (or a button calling `route.go`) replaces the page inside it: the browser keeps the document, the header is not mounted again, and the cart count follows the page. It is still a page load in meaning (the same document from the same server, the same state, a real `href`), only faster. See "Soft navigation and the shell" below, and `browser.test.mjs`, which drives the built site in a real Chrome.

```
pages/              page.js + view.js ("/"), product/[id]/page.js + view.js, checkout/page.js + view.js (+ rules.js), components/product-card.js (the list only, imported by view.js)
shared/             cart.js (the cart namespace), catalog.js (the products), plugins.js, shell.js (the shell's behavior: imported by every page.js), shell-view.js and components/ (the shell's content and the components: imported by the view.js files)
api.js              the server side: the cart and the orders (the durable data lives on the server)
```

Run it with `npm run example -- shop` (builds, then serves with `agent-ui serve` at http://localhost:8080/). `npm run example -- shop test` runs its tests (`browser.test.mjs` needs Chrome and skips itself without it).

**Why the framework's code and the shop's are two files.** They change at different times: the framework when you upgrade it, the shop's code on every deploy. In one file, a one-line change to `shared/cart.js` would make every returning visitor download the 10.7 KB (esbuild + gzip) of framework code again; as two files, they download the 1.1 KB of the shop's shared code and keep the rest. The price is one request more on the first visit, fetched in parallel with the others (`modulepreload`).

### How to read the numbers

- **Size** and **Gzip** are what the build itself reports for each file (`size.bytes` / `size.gzipBytes` in `dist/manifest.json`: our bundler's output — comments and indentation stripped, names kept — and gzip level 9 of it). **esbuild** is the same file after `transformSync(code, { minify: true, format: 'esm' })` (esbuild 0.28.2), the call `examples/events/build.config.mjs` hands to the `transform` option; this example does not declare esbuild, so the columns were measured with a one-off script that adds that `transform`. **esbuild + gzip** is gzip level 9 of the minified file. Every total is the arithmetic sum of the files it names. "All three pages as one bundle" is the sum of the chunks, an approximation of one file that held everything.
- **The shell and soft navigation cost about 2.8 KB per page here, and the shop pays it on every page.** Measured against the same site without them (the commit before the shell): the list page went from 14,338 to 17,108 bytes (esbuild + gzip, with its stylesheets), the product page and the checkout page by the same 2.8 KB. About 0.23 KB of that is in the runtime every page downloads (`destroy()` and the nested-app guards, `agent-ui` 7,871 to 8,102), about 2.6 KB is the shell machinery in the shared chunk (the shell, `syncApps`, the navigation plugin, the pages module's new parts, and the header's content as data), and each page's own chunk is about 80 bytes smaller, because the header is no longer repeated in every page's spec. A page that has no shell pays the 0.23 KB and about 0.3 KB more in `src/pages.js`, and nothing else (`shell.js`, `syncApps` and the navigation plugin are downloaded only by a page that lists a shell; the checks of both are left out of production builds like the other checks). What it buys: a click on a link no longer loads a document, the header and the runtime stay, and the page that appears starts from the state of the document it would have loaded.
- **The saving of the split itself is small, and that is the honest result.** Almost all of what a page downloads is the framework (the runtime, and the page and resource code in `agent-ui-checkout-index-product-id`), which every page needs; the view builders are the part no browser downloads. Moving them out of the browser is what changed against before the split: when the single bundle was split, opening the list went from 14,943 to 13,730 bytes (esbuild + gzip), about 8% less, and the shared chunk fell from 6,396 to 4,952 (these two numbers are from that change and were not re-measured; the figures above are current). The shop's own browser code is about 6 KB of source in the shared chunk (the cart, the catalog, the plugin, the shell) plus each page's behavior and its finished spec. The page-specific part is the `index`, `product-id` or `checkout` row: between 7% and 16% of a page, and a page leaves out the other two. Each page's own download got a little bigger (the list from 901 to 1,008 bytes), because its spec travels as data. The product page is bigger for a second reason: it lists the `withHead` plugin (`@ehtb/agent-ui/head`) because its head follows the state (canonical link and structured data), and only a page that lists it downloads it. The saving grows with the amount of view code: an app with many large components per page saves much more, while what every page pays anyway is about 22.4 KB (esbuild + gzip; it was about 12 KB before the shell, the head code and the navigation features joined the framework's shared code).
- **`build.test.mjs` asserts the split on the files that were written**: markers of the list page (`product-list`, `result-count`) are only in the `index` chunk, markers of the product page only in `product-id`, and markers of the checkout (`checkout-form`, `place-order`) only in `checkout`; the shared behavior modules (`cart.js`, `catalog.js`) are in the shared chunk and in no page chunk, the framework's modules are in no chunk that holds the shop's code, and no chunk's module list holds a `view.js`, the layout, a component or `@ehtb/agent-ui/spec`.

## How it works, technically

1. **A folder is a page.** The build finds every folder below `pages/` that holds a `page.js` (with a `view.js` beside it) and takes the URL from the path (`[id]` is one parameter segment). For each it generates a browser entry and a server module in `.agent-ui/` (never edited, gitignored by itself), so `build.config.mjs` lists no page, no base and no entry.
2. **The module graph starts from the behavior, not the view.** Each page's entry imports its `page.js` (behavior) and its finished `spec.js` (data), and the bundler reads every import from there (relative paths with extensions, named imports, package imports). `view.js` and everything only it imports (the layout, the components, the spec builders) are evaluated in Node when the site is built, so they are not in the graph at all. What is, is tagged with the set of pages that reach it: `pages/checkout/page.js` and `checkout/rules.js` only by checkout, `shared/cart.js` by all three pages, `shared/catalog.js` by the list and the product page.
3. **Modules with the same tag and the same owner share a chunk, and small chunks are folded together.** Reached by one page, a module of the shop joins that page's chunk. Reached by several, it goes to a `shared-` chunk; a module of the framework goes to an `agent-ui-` chunk instead (here `agent-ui-checkout-index-product-id`), and a module of an npm package to a `vendor-` chunk, so that the code that changes on every deploy and the code that changes on an upgrade are never one file. Grouping by the exact set of pages would make up to one chunk per combination of pages (here the cart, shared by all three, and the catalog, shared by the list and the product page); a chunk under `minSharedChunkBytes` (4096 bytes of source by default) is folded into a bigger chunk of the same owner (or of the shop) whose pages include all of its own, so that a site of many pages does not become dozens of tiny files. The price is that a page may download a few hundred bytes it does not use: here the checkout page carries the 1.2 KB of `catalog.js`. `build.test.mjs` also builds with `minSharedChunkBytes: 0` to show the exact split, where the checkout page never loads the catalog.
4. **Each page loads its chunks in a known order.** The HTML links the page's stylesheets and a `modulepreload` hint for every chunk, then the entry script. `manifest.json` records it (`chunksLoadedAtStartup`: `agent-ui`, `agent-ui-checkout-index-product-id`, the shared chunk, then the page's chunk), and the test reads it. The preload hints fetch all of them in parallel, so the chain does not become a waterfall.
5. **A page asks for what it needs, and only that.** The list and product pages list the `catalog` namespace, so they load `/products.json`; the checkout page does not list it, so it never asks. Every page lists the `cart` namespace and the resources plugin (`shared/plugins.js`), because the header shows the cart.
6. **Durable data is on the server.** The cart lives in `api.js`. A page asks for it when it opens (`cart` resource), and every change (`cart.add`, `cart.remove`) is a request that waits in a queue and is sent in order; the server's answer is the new cart. The checkout sends the order to `POST /api/order`, which validates it again with the same `rules.js` and empties the cart, and the page then asks for the cart again (`calls: ['cart.reload']`). The server renders each page with the cart it holds (`server-fetch.mjs` answers the page's requests in process), and the browser takes over.
7. **Moving between pages is a page load, or a soft one.** The links are real `<a href>`; the pages are rendered per request (one URL per product) and the chunks are hashed, so the next page arrives finished and finds the runtime, the framework's chunk and the shared chunk in the cache. A link written `soft: true` (and the product page's "Go to checkout" button, which calls `route.go`) skips the document load: see the next section.

## Soft navigation and the shell

`shared/shell.js` defines the shell (`defineShell`): a name, its own namespace `frame` (`frame.cartCount`, which the header shows), the navigation plugin, and one `reads` entry, `cart.count` of the page into `frame.setCartCount`. `shared/shell-view.js` is its content: the header with the links (the current one is marked from `route.path`), `pageSlot()` where the page goes, and the footer. Each page's `page.js` lists `shell`, each `view.js` exports it, and every page lists the `cart` namespace the shell reads.

- **What a click does.** A click on `nav-checkout` (a soft link in the footer) fetches `/checkout` (the rendered document), reads the state and the page script from it, adds `checkout.css`, imports the `checkout` chunk, destroys the list page's app and starts the checkout page in the same element, pushes `/checkout`, tells the shell the path and moves the focus to the page. The header's element, its app and the runtime are the same ones afterwards, and the badge follows the cart of whatever page is showing. The browser loaded one document.
- **Where it falls back.** A link to a URL that answers 404, a redirect, a page that has another shell, or a failed import ends in a normal page load of the same URL, with the reason in the console. `agent-ui check` reads the links of the pages and of the shell and reports a soft link to a page of another shell.
- **Proof.** `app.test.mjs` shows the shell's header following the cart of the page (on the shim). `browser.test.mjs` builds the site, serves it with the render server and drives headless Chrome over the DevTools protocol (Node's own WebSocket, no library): the page replaced and the document kept (a mark set on the document, on the header's element and on the shell's app is still there), the stylesheet of the old page removed and the new one added, the title of the product page following it, the badge following the cart, `route.go` from a button, back and forward, exactly one document load, nothing in the console, and the fallback for a 404. It skips itself when there is no Chrome (`CHROME_PATH` names one).

## Limitations

- **A soft link starts the next page afresh.** The header stays, but the page is a new app, as after a load: anything not kept on the server or in the shell (a search text, a half-filled form) is gone. The cart survives because it is on the server. Back and forward return to the scroll position the visitor left; there is no prefetch of the next page and no transition between pages. A link without `soft`, and any link in a browser without JavaScript, is a normal page load.
- **Code is split by page, not inside a page.** Everything a page lists is in its chunk. A heavy feature inside one page can be fetched with a plain `import()` (a lazy chunk), as the state panel is.
- **The page's spec is per page; the shell's content is once.** A page's finished spec travels in its chunk as data. The shell's content (header, badge, footer) is written once, as data, in the shared chunk, so it is no longer repeated in every page.
- **No tree shaking.** The bundler includes whole modules, so a component is its own module and a view imports only the ones it uses. A file that re-exports many components (`index.js`) would load all of them whenever a view is built, and re-exports are a build error in this dialect. Measured with esbuild's tree shaking on `examples/events`, it saved under 1%.
- **The framework is most of the size.** About 21 KB (esbuild + gzip: the runtime and the framework's page, resource and shell code) is paid by every page, once. Page-specific savings only matter when pages carry a lot of their own UI.
- **The shared stylesheet is one file, the page styles are not shared.** A page's own styles are in `page.css` next to it and load only with that page.
- **One cart for the whole server.** This demo has no sessions: `api.js` keeps a single cart, and every page embeds that cart. A real shop keeps a cart per visitor (a session cookie); nothing in the pages would change.
- **It needs a server.** The cart and the orders are answered by `api.js`, so the shop runs with `agent-ui serve` (or your own server using `api.js`); it has a page with parameters, so it is not a static site.
- **Browser behavior is checked in one Chrome, timing was not measured.** `browser.test.mjs` runs the soft navigation in headless Chrome; the other tests run the pages on the DOM shim and read the files the build wrote. Page-load and swap timing were not measured.

## Tests

`npm run example -- shop test` runs `app.test.mjs` (the three pages and their shell against the real `api.js`: the catalog and the cart, the queue of cart changes, the cart carried to the next page and shown in the header, 404 for an unknown product, the order and its validation on both sides), `build.test.mjs` (the chunk assertions above, including the exact split and the shell shipped once), `conformance.test.mjs` (the specs and the shell's content pass the validator and the JSON Schema) and `browser.test.mjs` (soft navigation in real Chrome, skipped without one).
