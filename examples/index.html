Examples

Examples

Complete agent-ui apps, from the smallest page to a production server.

Edit this page on GitHub↗

Complete apps that use agent-ui the way a project does. They are separate projects with their own package.json, so they show the library next to other tools without the framework depending on any of them.

ExampleWhat it showsRun it
basic↗The minimal page: pages/page.js (behavior) and pages/view.js (content) are /; two namespaces (todos, filter), one reading the other.npm run example -- basic
notes↗The quick start from docs/API.md: notes and composer, a cross-namespace calls. In memory: durable data belongs on the server.npm run example -- notes
contacts↗Forms and validation in four namespaces (contacts, form, view, editing); calls between them.npm run example -- contacts
todomvc↗The official TodoMVC spec (minus persistence and routing, which do not apply) in four namespaces; a list of two handlers on one event; a benchmark; a user session run in the test shim and in real Chrome with the results compared step by step (skips without Chrome).npm run example -- todomvc
directory↗Two pages (/ and /person/:id) sharing an async resource; URL parameters, nested lists.npm run example -- directory
hydration↗Server rendering and takeover: every URL rendered per request, a 404 for an unknown article, route.hydrated.npm run example -- hydration
registration↗A complex form: fields that show, hide and fill each other, a collapsible panel, a country list and per-country regions fetched from the server, validation that follows what is on screen.npm run example -- registration
react-converted-components↗A shadcn-style component library converted from React originals: variants, optional props, slots, field state as namespaces made by reusable features (the counterpart of custom hooks), mistakes refused with suggestions. A second page (/primitives) builds the interactive primitives React takes from a library — a popover with a focus trap, a combobox, a date picker and a drag list — as namespaces instead of component state. A third page (/charts) draws a Chart.js chart into one element with a plugin (mountElement), tested in headless Chrome; it depends on Chart.js from the npm registry.npm run example -- react-converted-components
loading-states↗Pages that say when they are ready: ready, pending, status, background refresh, a failed load as a finished state, 404 for an unknown id.npm run example -- loading-states
orders↗A multistep flow: customer, then orders, then shipment, as chained resources across namespaces; a reusable loadable namespace; stale responses ignored; a validated form with notes kept in memory.npm run example -- orders
shop↗Code splitting, and soft navigation. Three pages (list, product, checkout) that share a shell (header and footer that stay while a soft: true link or route.go replaces the page; a real-Chrome test), components and a cart that lives on the server. Every page is its own entry, so a page downloads only what it imports and the code its pages share. Its README has the sizes (plain, gzip, esbuild, esbuild + gzip), what is downloaded once and what per page, the size of every module, how the split works and its limits.npm run example -- shop
events↗The largest example: one folder per page, per-page APIs from compose-api.js (a file to copy: the server side is plug-in, the framework only asks for an api object), different layouts, specific and wildcard URLs that resolve by specificity, declared head, static pages, forms that work without JavaScript, prerendering, and takeover by the browser app.npm run example -- events
islands↗agent-ui as a library, without its page model: a plain node:http host owns the page, renders two apps into it with renderPage and writes their state next to them; the browser loads the package's modules through an import map, with no build; syncApps sends the catalog's count to the header badge. A real-Chrome test.npm run example -- islands
production-server↗A production host with no dependencies: Node's http serves the built files from memory (ETags, immutable hashed assets), createSsrHandler renders every page per request, security and CDN cache headers go on every answer, /healthz, graceful shutdown, and a Dockerfile.npm run example -- production-server
with-express↗agent-ui pages inside an Express server that owns the routes and the API.npm run example -- with-express
with-fastify↗The same inside a Fastify server.npm run example -- with-fastify
with-typescript↗TypeScript and zod: one zod schema per kind of data gives the types (z.infer, checked with tsc and checkJs) and checks the answers of the resources (response: Tasks.parse) and the requests of the server.npm run example -- with-typescript
with-tailwind↗Tailwind CSS: utility classes in the spec, generated pages/page.css, a test that checks every class.npm run example -- with-tailwind

Run one locally

Clone the repository, install the dependencies of that example, then run its scripts. The dependency-free examples run from the repository root with npm run example.

terminal
git clone https://github.com/ehtb/agent-ui.git
cd agent-ui
npm run example -- basic test
npm run example -- basic dev

Examples with their own dependencies (events, with-typescript and react-converted-components) are skipped by the root test run. Install them inside their folder and run the example through the same command.

Which one should I copy?

Start with basic for the smallest page, notes for two namespaces that change together, and registration for a form. Use directory for server data and URL parameters, hydration for the browser handoff, and shop when several apps share chunks. The production-server example is the model for deploying behind your own Node server.
